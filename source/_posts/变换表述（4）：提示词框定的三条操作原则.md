# 提示词框定的三条操作原则（2026 迭代版）
## ——当模型能力持续增强，Agent 系统应该如何重新分配控制责任？

### 引言：一个需要重新思考的问题

提示词设计中有一个长期存在的判断：**提示词的有效性取决于它与任务结构的匹配程度，而不是措辞有多精致。**

这个判断在 2025—2026 年的模型迭代中仍然成立，但它的工程含义正在发生变化。

过去，提示词设计的一项重要工作，是替模型补足它不擅长的能力：把复杂任务拆解成步骤，明确规定执行顺序，通过大量规则减少错误，使用示例约束输出格式。

随着基础模型的推理、规划和情境判断能力增强，这些做法的边际收益开始发生变化。一部分过去有效的规则，可能不再提供额外帮助，甚至会限制模型根据具体情境自主判断的空间。

Anthropic 在 2026 年 7 月发布的 Claude Code 上下文工程实践中提到，他们针对 Claude Opus 5 和 Claude Fable 5，将 Claude Code 的系统提示词删减了超过 80%，在其代码评测中没有观察到可测量的性能损失。

这项实践揭示了一个值得重视的变化：模型能力提升之后，过去用于弥补模型判断不足的部分规则，可能已经成为冗余约束。规则之间的重复和冲突，也会增加模型处理上下文的负担。

与此同时，推理模型逐渐具备自主分解问题、尝试不同求解路径和修正错误的能力。对于这类模型，机械地要求逐步思考、重复描述通用推理过程，往往不再是必要的设计。

但这并不意味着应用层应该放弃约束。

模型能够自主规划，不代表它知道业务系统的全部规则；模型能够调用工具，不代表它能够保证操作正确；模型能够完成多步任务，也不代表整个执行过程具备可靠性。

因此，真正需要重新思考的不是如何进一步简化提示词，而是：

**当模型能力持续增强，应用层应该把哪些决策交还给模型，又应该在哪些地方保留确定性的控制？**

本文将这一问题归纳为三条操作原则：

1. 最小必要的语义锚定：明确模型必须理解的信息，不重复描述它已经具备的通用能力。
2. 约束的正确分层：将约束放在最有能力保证其执行的系统层面，而不是全部堆叠在提示词中。
3. 自主性与控制强度匹配：根据模型能力、任务性质和错误代价，决定模型可以自主决定什么。

这三条原则共同指向一个变化：从设计一段尽可能完整的提示词，转向设计一套合理分配控制责任的 Agent 系统。

## 一、原则一：最小必要的语义锚定

### 从堆叠专业术语到精确锁定语义边界

提示词首先需要解决的问题，不是告诉模型应该如何思考，而是确保模型正确理解当前任务。

模型面对一个任务时，可能存在多种合理解释。提示词的作用之一，就是缩小这些解释之间的歧义，明确哪些信息不能被错误理解。

例如：

- 「分析订单」可能指统计订单数据，也可能指分析单个订单的异常。
- 「完成退款」可能指提交退款申请，也可能指确认资金已经退回。
- 「优化代码」可能指提升性能，也可能指改善可维护性。
- 「记住用户信息」可能指保存长期偏好，也可能指保留当前对话中的临时信息。

这些问题并不是模型缺乏推理能力，而是任务本身存在语义边界不明确的问题。

因此，领域术语、类型标注和必要的上下文仍然具有重要价值。

但需要注意：专业术语并不是越多越好。

当模型已经能够根据上下文正确理解某个概念时，重复定义、反复解释和堆叠同义规则，并不会带来相应的性能收益。

真正有效的语义锚定，应该集中在模型无法可靠推断的信息上。

例如：

**不够精确的表达：**

> 请分析用户的记忆信息，找到相关内容，并生成回答。

**更好的表达：**

> 根据当前任务意图，从长期记忆中检索与本次任务直接相关的用户事实。不要将历史对话中的临时信息当作长期偏好，也不要使用与当前任务无关的记忆。

第二种表达没有增加复杂的推理步骤，而是明确了记忆的类型、使用边界和任务相关性。

### 语义锚定的三个判断标准

**1. 术语是否具有实际区分能力？**

如果一个专业术语能够排除其他可能的解释，就值得使用。

如果它只是重复模型已经理解的信息，就没有必要保留。

**2. 是否明确了任务的真实目标？**

模型应该知道最终需要解决什么问题，而不仅仅是知道用户使用了什么表达。

例如，「总结会议」和「从会议中提取待办事项并识别负责人」是两个不同的任务。

**3. 是否明确了不可自行推断的信息？**

业务定义、数据口径、用户授权和特定领域的约束，不能假设模型一定能够从常识中推断出来。

### 实践原则

对能力较强的模型，优先提供：

- 清晰的任务目标。
- 必要的领域概念。
- 关键业务定义。
- 不可自行推断的上下文。
- 明确的成功标准。

减少：

- 通用推理能力的重复描述。
- 没有实际区分价值的专业术语。
- 大量同义表达。
- 对模型已有能力的机械性规定。

**判断标准：这段信息是否提供了模型无法从现有上下文中可靠获得的增量信息？**

如果没有，就应该考虑删除。

## 二、原则二：约束的正确分层

### 从提示词规则列表转向系统结构设计

传统 Prompt Engineering 倾向于通过规则列表控制模型行为。

例如：

- 必须按照指定顺序执行。
- 不允许调用未授权工具。
- 不允许跳过任何步骤。
- 不允许输出指定格式之外的内容。
- 必须在任务完成后才能返回结果。

这种方式在早期模型上具有一定价值，但在 Agent 系统中，单纯依赖提示词控制行为存在明显局限。

原因很简单：

**提示词可以指导模型遵守规则，但不能独立保证规则一定被执行。**

例如，在提示词中写明「禁止删除生产数据」，并不意味着系统已经具备可靠的生产数据保护能力。

真正可靠的做法，是让模型根本没有直接执行未授权删除操作的权限，或者通过独立的审批和校验机制控制操作。

因此，约束应该放在最有能力保证其执行的系统层面。

### 约束的五个层次

| 层次 | 主要职责 | 典型约束 |
|---|---|---|
| Schema | 约束数据结构 | 必填字段、类型、枚举值 |
| Tool | 约束可执行操作 | 参数校验、权限范围 |
| Runtime | 约束执行过程 | 状态转换、并发、重试 |
| Prompt | 约束模型判断 | 决策依据、业务规则 |
| Evaluator | 验证执行结果 | 任务成功、规则违反、结果质量 |

这五个层次并不是严格的技术架构分层，而是约束责任的划分方式。

举一个简单的例子。

假设 Agent 需要管理多个待办任务，每个任务有三种状态：

`pending`、`in_progress`、`completed`

Schema 可以保证状态字段只能使用规定的枚举值。

Tool 可以限制模型只能通过指定接口修改任务状态。

Runtime 可以保证状态转换符合业务规则，例如不能直接从 `pending` 跳转到 `completed`，或者不能同时执行多个互斥任务。

Prompt 可以告诉模型，在任务尚未真正执行成功之前，不应该将其标记为完成。

Evaluator 则负责检查最终状态是否与实际执行结果一致。

可以看到，模型只需要理解必要的业务判断规则，其他能够通过确定性程序保证的约束，就不应该完全依赖模型。

### 哪些约束应该留在提示词中？

并不是所有约束都可以通过 Schema 或工具接口解决。

提示词仍然需要承担模型决策层面的责任，尤其是以下三类约束。

**1. 裁决规则**

当多个目标或规则发生冲突时，模型应该依据什么进行判断？

例如：

- 用户当前明确提出的要求优先于历史偏好。
- 安全要求优先于任务完成速度。
- 当前任务目标发生变化时，需要重新评估原计划。

**2. 不可逆操作边界**

哪些操作需要人工确认？

例如：

- 删除重要数据。
- 发送正式通知。
- 执行资金交易。
- 修改生产环境配置。

需要强调的是，提示词负责让模型识别这些边界，真正的权限控制和审批流程必须由 Runtime 或业务系统保证。

**3. 跨轮次目标守恒**

在长时间、多轮次的任务执行过程中，哪些目标和约束不能发生变化？

例如：

- 用户的原始目标不能被执行过程中的局部任务替代。
- 不允许因为工具失败而擅自扩大授权范围。
- 用户修改目标后，旧计划必须重新评估。

### 一个重要的设计原则

Anthropic 在 Claude Code 的实践中强调了工具接口设计、渐进式上下文加载、自动记忆和参考工件的重要性。

这背后的工程思想值得借鉴：

与其不断告诉模型如何使用工具，不如把工具设计得更容易被正确使用；与其在系统提示中重复描述所有信息，不如根据任务需要加载相应的技能和参考资料。

但这并不意味着 Schema 可以代替所有提示词，也不意味着工具接口能够自动解决业务逻辑问题。

真正重要的是：

**将约束放在最有能力保证它被执行的层面。**

## 三、原则三：自主性与控制强度匹配

### 从规定求解路径到划定自主决策空间

这是推理模型和 Agent 系统发展之后，提示词设计发生变化最明显的地方。

传统提示词通常需要明确规定任务步骤。

例如：

1. 首先分析输入。
2. 然后拆解问题。
3. 接着逐步执行。
4. 最后检查结果。
5. 按指定格式输出。

对于推理能力较弱的模型，这种方式可能有助于提高任务完成率。

但对于推理原生模型，过度规定通用推理过程可能产生负收益。

这类模型通常已经具备自主分解问题、选择求解路径和修正错误的能力。

因此，对于一般任务，应该优先让模型自主选择求解路径，而不是替模型预先设计完整的推理过程。

但这里必须明确一个区别：

**模型可以自主决定如何完成任务，不代表模型可以自主决定业务规则和执行权限。**

例如，用户要求 Agent 取消订单并申请退款。

模型可以自主规划：

- 查询订单。
- 判断订单状态。
- 确定可用的售后路径。
- 发起相应申请。
- 检查处理结果。
- 通知用户。

但是，以下内容不能仅仅交给模型自主判断：

- 哪些订单允许取消。
- 哪些退款必须经过风控审核。
- 哪些操作需要人工审批。
- 用户是否具有相应操作权限。
- 哪些操作不可逆。

这里真正需要划分的是：

- 求解路径：模型可以拥有较大的自主权。
- 业务不变量：系统必须明确保证。
- 执行权限：由工具和 Runtime 控制。
- 最终结果：必须经过验证。

### 1. 根据模型能力调整框定深度

不同模型的自主规划能力不同。

对于指令跟随能力较弱的模型，可能需要更多示例、步骤和输出约束。

对于推理能力较强的模型，则应该减少不必要的过程指令，重点提供目标、条件和判断标准。

但不应该仅凭模型是否属于推理模型来决定框定程度。

最终应该通过目标模型上的实际评测确定。

### 2. 根据任务性质调整自主空间

任务的收敛性和发散性仍然是重要的判断依据。

**收敛任务**

例如代码修复、数据提取、订单处理。

目标明确，结果通常可以验证。

设计重点是明确输入、输出、约束和成功标准，允许模型在边界内自主选择路径。

**发散任务**

例如产品设计、技术架构、商业策略。

存在多个合理答案，过度限制模型的探索空间可能降低结果质量。

设计重点是明确目标、评价维度和不可违反的条件，保留必要的探索空间。

**混合任务**

例如 Agent 自动开发、技术方案实施、复杂业务流程。

这类任务通常同时包含探索和执行两个阶段。

模型可以在分析和规划阶段拥有较大的自主性，但在执行不可逆操作时，需要切换到更严格的控制模式。

### 3. 根据错误代价调整控制强度

模型能力不是决定框定强度的唯一因素。

还必须考虑任务的错误代价和操作可逆性。

| 任务 | 错误代价 | 推荐控制策略 |
|---|---|---|
| 文章摘要 | 低 | 目标导向，弱约束 |
| 内容创作 | 低 | 保留较大生成自由度 |
| 技术方案设计 | 中 | 明确约束和验收标准 |
| 代码修改 | 中高 | 自主规划，测试验证 |
| 数据库迁移 | 高 | 显式审批、状态校验、回滚 |
| 支付与退款 | 很高 | 权限控制、业务规则、人工审批 |

由此可以得到一个重要结论：

**模型能力越强，不代表系统应该给予它越大的执行权限。**

自主规划能力与执行授权是两个不同的问题。

模型可以负责提出方案，但不一定有权执行方案；模型可以判断某个操作可能合理，但不一定有权直接实施。

### 4. 多轮 Agent：框定计划状态，而不是机械规定步骤

在 Agent 场景中，框定的对象还需要从单次任务扩展到持续执行过程。

多轮 Agent 面临的主要问题，不只是能否完成单个步骤，还包括：

- 是否持续记住原始目标？
- 是否正确理解当前执行状态？
- 是否知道哪些任务已经完成？
- 是否能够识别阻塞和失败？
- 是否能根据用户的新要求调整计划？

因此，系统需要为长期任务维护一个明确的状态表示。

一个实用的最小结构可以是：

| 字段 | 含义 |
|---|---|
| Goal | 原始任务目标 |
| Done | 已完成事项及其证据 |
| Current | 当前执行任务 |
| Pending | 后续待执行任务 |
| Blocked | 当前阻塞原因 |
| Constraints | 必须持续遵守的约束 |

这里最重要的是完成状态必须有证据。

例如：

- 发起退款申请，不等于退款成功。
- 提交代码，不等于测试通过。
- 调用日程创建接口，不等于日程已经成功创建。
- 发送邮件请求，不等于邮件已经成功发送。

Agent 应该根据工具返回结果或外部系统的实际状态确认任务完成，而不是根据自己的执行意图推断完成。

对于简单任务，不需要引入复杂的计划状态管理；只有当任务跨越多轮、涉及多个工具或存在明显的目标漂移风险时，才值得维护这样的状态结构。

### 实践原则

- 让模型自主决定通用求解路径。
- 显式规定领域特定的业务规则。
- 将不可逆操作交给确定性权限控制。
- 根据错误代价调整自主决策空间。
- 在多轮执行中维护目标和真实状态。

判断标准不是模型能不能完成任务，而是：

**哪些决策可以安全地交给模型，哪些决策必须由系统保证？**

## 四、从单次输出到分布鲁棒性：重新定义框定效果

前三条原则解决的是如何设计框定。

但一个更重要的问题是：如何证明这种设计真的有效？

传统 Prompt 评估通常关注某次输入能否得到满意结果。

这种方式存在明显局限。

一个 Prompt 在固定测试用例上表现良好，不代表它能够应对真实用户的表达变化、任务变化和环境变化。

2026 年的两项研究，为这一问题提供了值得关注的证据。

### 1. 语义锚定与提示稳定性

Xie 等人在 ACL 2026 Findings 发表的研究《Beyond Prompt Engineering: A Systematic Analysis of Prompt Lexical Sensitivity and Its Impacts on Quality》，使用 132,000 个提示变体研究语言表达变化对模型性能的影响。

研究提出了 Prompt Performance Stability 的缩放规律，并识别出两个影响稳定性的语言因素：

- Domain-Specific Terminology：领域特定术语，有助于锚定语义边界。
- Explicit Action Directives：明确的行动指令，有助于明确任务要求。

其自动化提示优化方法在特定代码生成实验中报告了 40.7% 的性能方差降低。

这说明，必要的语义锚定和行动约束可能改善模型在不同提示表达下的稳定性。

但需要注意，这个结果来自特定实验设置，不能直接推导为所有任务、所有模型都能够获得相同的稳定性收益。

另外，性能方差降低也不等于任务成功率必然提高。稳定性和平均性能应该分别评估。

### 2. 用户分布变化与模型性能退化

Seegmiller 和 Preum 在 ACL 2026 发表的研究《Measuring Distribution Shift in User Prompts and Its Effects on LLM Performance》，提出了 LENS 评估框架。

研究覆盖了：

- 192 个真实部署环境中的提示分布偏移场景。
- 81 个模型。
- 468 万条训练提示。
- 5.76 万条评估提示。

研究报告称，中等程度的用户提示行为分布偏移，与部署模型平均 73% 的性能损失相关。

这里需要特别区分两个概念：

**提示表述变化，不等于用户分布变化。**

提示表述变化，是指在语义和任务保持一致的前提下，用户使用了不同的措辞。

例如：

- 请总结这篇文章。
- 帮我概括文章的核心内容。

用户分布变化，则可能意味着用户群体、地域、时间和任务类型发生变化。

例如：

- 原来主要由专业工程师使用，后来普通消费者开始使用。
- 原来用户主要询问技术问题，后来开始提出业务咨询。
- 原来用户习惯提供完整背景，后来只输入简短的口语化需求。

两者需要采用不同的评估方法。

前者主要检验提示表达鲁棒性，后者主要检验真实部署环境中的分布鲁棒性。

### 3. 建立两个层次的稳定性评估

建议将 Agent 的稳定性评估拆分为两个层次。

**第一层：语义等价表达稳定性**

在任务目标和条件不变的前提下，构造多种自然表达方式，检查模型能否保持相近的任务理解和结果质量。

重点观察：

- 意图识别是否一致。
- 关键事实是否遗漏。
- 输出结构是否稳定。
- 工具调用是否发生不合理变化。
- 任务成功率是否明显下降。

**第二层：真实用户分布稳定性**

通过真实用户数据，观察不同用户群体、时间周期和任务类型变化对系统的影响。

重点观察：

- 用户意图分布是否变化。
- 新任务类型是否出现。
- 工具调用分布是否异常。
- 任务成功率是否退化。
- 业务规则违反率是否上升。

这两层评估不能相互替代。

### 4. 重新定义框定质量

因此，框定的目标不应该只是让模型在某个固定提示下得到正确答案。

更合理的目标是：

**在合理的输入变化和任务环境变化下，维持可接受的任务成功率、行为边界和执行可靠性。**

这也是为什么提示词不能仅靠设计者主观判断，而应该进入持续评测和迭代流程。

## 五、三条原则的最终表述

经过以上调整，可以将三条原则总结为：

### 原则一：最小必要的语义锚定

框定的首要任务是明确模型必须理解、但无法从现有上下文中可靠推断的信息。

使用必要的领域术语、类型标注和业务定义，缩小语义歧义。

避免重复描述模型已经具备的通用能力，也不要通过术语堆叠制造虚假的精确性。

**核心问题：模型需要额外知道什么，才能正确理解任务？**

### 原则二：约束的正确分层

约束不应该全部堆叠在提示词中，而应该放在最有能力保证其执行的系统层面。

Schema 负责数据结构，Tool 负责可执行操作，Runtime 负责执行过程，Prompt 负责模型判断，Evaluator 负责结果验证。

对于无法通过确定性接口表达的裁决规则、业务判断和跨轮次目标约束，仍然需要在提示词中明确。

**核心问题：这条约束应该由系统的哪一层负责保证？**

### 原则三：自主性与控制强度匹配

框定的目的不是规定模型完成任务的每一个步骤，而是合理划定模型的自主决策空间。

对于低风险、可逆任务，释放模型的自主规划能力。

对于中高风险任务，允许模型自主规划，但必须增加结果验证。

对于高风险、不可逆任务，通过权限控制、业务规则和人工审批保证执行安全。

**核心问题：哪些决策可以交给模型，哪些必须由系统确定？**

## 六、工程实践：如何验证一套框定设计是否有效？

上述三条原则如果只停留在设计理念层面，就很容易变成另一套抽象的方法论。

真正有价值的是将其转化为可以验证的工程流程。

建议采用一个简单的实验方法：

**同一个任务，设计三种不同强度的框定，比较真实交付质量。**

### 1. 三组实验

| 实验 | 框定方式 | 包含内容 |
|---|---|---|
| A：弱框定 | 目标导向 | 任务目标、必要上下文、交付要求 |
| B：中等框定 | 约束导向 | 目标、业务约束、成功标准、异常边界 |
| C：强框定 | 流程导向 | 目标、约束、显式步骤、决策规则、异常处理 |

在相同模型、相同工具环境和相同任务数据上进行对比。

### 2. 统一评估指标

| 指标 | 评估内容 |
|---|---|
| 任务成功率 | 是否真正完成用户任务 |
| 业务规则违反率 | 是否违反必要的业务约束 |
| 语义鲁棒性 | 不同表达下是否保持稳定 |
| 工具调用正确率 | 是否正确选择和使用工具 |
| 结果验证通过率 | 最终结果是否得到外部证据确认 |
| 执行成本 | Token、工具调用和计算成本 |
| 完成时间 | 从请求到有效结果的时间 |
| 不可逆错误率 | 是否发生不可恢复的错误操作 |

需要注意，稳定输出错误答案也可能具有很低的方差，因此不能只看稳定性指标。

### 3. 增加两类测试

**模型变化测试**

相同的框定设计，分别在不同能力层级的模型上运行。

观察哪些规则已经没有增量价值，哪些规则仍然是必要约束。

**任务分布变化测试**

使用语义等价改写、不同用户表达、边界条件和异常任务进行测试。

观察系统在固定测试集之外是否仍然可靠。

### 4. 确定最终框定策略

最终选择不应该简单地追求最短提示词，也不应该追求最高的单次成功率。

而应该综合考虑：

- 任务成功率。
- 行为可靠性。
- 输入变化下的稳定性。
- 执行成本。
- 错误代价。

对于低风险任务，可以接受一定的输出变化，换取更低的执行成本。

对于高风险任务，即使需要更多的规则和验证，也应该优先保证行为可靠性。

**框定的好坏，最终应该由真实任务中的交付质量决定，而不是由提示词的长度决定。**

## 七、实践检查清单

在设计或评审 Agent 提示词时，可以使用以下清单。

### 语义边界

- [ ] 任务目标是否明确？
- [ ] 是否使用了必要的领域术语和类型定义？
- [ ] 是否存在模型无法自行推断的业务信息？
- [ ] 是否重复描述了模型已经具备的通用能力？
- [ ] 成功标准是否可以被验证？

### 约束分层

- [ ] 数据结构约束是否放在 Schema 中？
- [ ] 操作权限是否由 Tool 和 Runtime 保证？
- [ ] 状态转换是否具有确定性校验？
- [ ] 提示词中保留的规则是否确实需要模型参与判断？
- [ ] 是否存在重复、冲突或过时的规则？
- [ ] 最终结果是否经过独立验证？

### 自主性与风险

- [ ] 模型是否可以自主选择通用求解路径？
- [ ] 是否明确了不可违反的业务规则？
- [ ] 是否区分了规划权限和执行权限？
- [ ] 是否评估了错误代价和操作可逆性？
- [ ] 不可逆操作是否具有必要的审批机制？
- [ ] 多轮任务是否能够维持原始目标和真实执行状态？

### 稳定性

- [ ] 是否测试了语义等价的不同提示表达？
- [ ] 是否覆盖不同用户表达习惯？
- [ ] 是否测试异常任务和边界条件？
- [ ] 是否比较过不同模型上的表现？
- [ ] 是否同时评估平均性能和结果方差？
- [ ] 是否建立了持续评测机制？

## 结语：从提示词设计走向 Agent 控制责任设计

2025—2026 年的模型迭代，并没有让提示词框定失去价值，而是改变了它在整个 AI 系统中的职责。

当模型具备更强的推理、规划和情境判断能力时，应用层没有必要继续替模型完成所有可以自主完成的工作。

过去依靠大量提示词规则弥补模型能力不足的方式，应该逐渐转向更精确的语义锚定、更合理的约束分层，以及更灵活的自主决策空间。

但模型能力增强，并不意味着系统可以放弃控制。

模型能够自主规划，不代表它了解全部业务规则；模型能够调用工具，不代表它拥有执行权限；模型能够生成正确答案，也不代表整个执行过程具备可靠性。

因此，成熟的 Agent 工程设计需要重新划分控制责任：

- 将通用推理和求解路径交给模型。
- 将结构约束交给 Schema 和接口。
- 将执行权限与状态管理交给 Runtime。
- 将必要的业务判断规则交给模型和业务策略共同处理。
- 将最终行为质量交给独立评估和验证机制。

这三条原则最终可以归纳为一个判断：

**好的 Agent 设计，不是尽可能多地告诉模型应该怎么做，而是准确划分模型的自主决策空间与系统必须保证的行为边界。**

在正确的地方给予模型自由，在必须确定的地方保持确定性。

这才是从 Prompt Engineering 走向成熟 Agent Engineering 的重要一步。
