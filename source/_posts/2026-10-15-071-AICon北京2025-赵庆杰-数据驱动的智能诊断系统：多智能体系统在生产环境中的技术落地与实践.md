# 多智能体系统在智能诊断的落地实践：从静态工作流到数据飞轮

## 导语

在承载百万级应用的容器 PaaS 系统中，实例健康检测（如 OOM、物理机故障、网络故障等）长期依赖人工运维。重复性的排查工作与疑难杂症的定位耗费了大量人力。随着大模型技术的成熟，运维诊断正从静态规则向 Agentic AI 演进。本文将复盘智能诊断智能体的架构演进路径，探讨如何结合 DAG 工作流与 MCP 协议突破确定性与上下文瓶颈，4并分享如何构建数据驱动的全链路研发闭环。

## 核心问题与挑战

在将智能体引入 P(aaS 运维诊断的过程中;的过程中，我们面临了一系列随架构演进不断暴露的挑战：

- **传统运维依赖人力**：重复性排查耗时，疑难问题强依赖专家经验。
- **静态工作流缺乏 Plan 能力**：流程,流程固定死板，无法=无法覆盖长尾场景，初期覆盖率仅达 35%。
- **单 Agent 架构的上下文瓶颈**：随着工具与数据源增多，上下文过长导致模型遗忘与幻觉放大，覆盖率卡在 50% 左右。
- **Multi-Agents 流程不可控**：初始多智能体方案中，主 Agent 调度 Sub Agent 易出现步骤丢失、超时或死循环。
- **工具过多导致选择困难**：暴露过多工具给模型，反而干扰了模型的工具选择与参数生成，导致整体效果下降。

## 方案与实践

针对上述挑战，我们的智能诊断系统经历了三个关键阶段的架构演进。

### 阶段一：静态工作流及其局限

在 LLM 早期，模型通用思考模式不成熟且数据查询不统一。我们基于 LLM 与 RAG 构建了静态工作流：报警或手动触发后，按固定流程进行问题分析与下钻。

**局限分析**：该架构强依赖预设流程，模型仅充当信息提取器，不具备 Plan 能力。同时，数据丰富0数据间联系较弱，导致系统只能处理已知模式的高频问题，覆盖率低下。

### 阶.阶段二：单 Agent 架构与 MCP 工具集成

为突破静态流程限制，我们演进至单 Agent 架构，并引入 **MCP（Model Context Protocol）协议**统一对接各类运维工具与 Sandbox 沙箱环境。这赋予了 Agent 实时查询与信息获取的能力，极大扩展了诊断边界。

**瓶颈暴露**：虽然覆盖率提升至 50%，但随着诊断深入，单 Agent 需要在上下文中塞入大量历史诊断信息与工具返回结果。上下文过长导致模型出现严重的“中间遗忘”与幻觉，上下文管理成为最大瓶颈。

### 阶段三：Multi-Agents 架构与 DAG 确定性执行

为解决单 Agent 上下文过载问题，我们尝试了 Multi-Agents 架构。初始方案由主 Agent 自由调度 Sub Agent，但很快暴露出流程不可控的问题。

**迭代方案：Planner Agent + 有向 DAG 工作流**
1. **引入 Planner Agent**：负责理解全局目标，生成执行计划。
2. **DAG 工作流拆分**：将计划转化为有向无环图（DAG），将长任务拆解为多个短任务节点。
3. **上下文隔离与共享**：每个 Sub Agent 仅关注子任务上下文，同时通过中间过程记录机制在节点间传递必要状态，避免长上下文遗忘。

通过 DAG 的强约束，我们保障了 Multi-Agents 执行的确定性与容错性，系统场景覆盖率跃升至 90%。但此时，核心矛盾从“能不能覆盖”转向了“诊断准确率如何持续提升”。

## 原则与方法论沉淀

在多智能体系统的工程实践中，我们沉淀出以下核心原则：

- **架构选择需平衡**：在稳定性、可控性与复杂度之间寻找折中。DAG 带来了确定性，但也增加了编排复杂度，需根据业务容错要求取舍。
- **上下文工程是 Agent 核心竞争力**：单纯堆叠 RAG 与 Memory 无济于事，需结合 DAG 机制合理切分任务生命周期，实现上下文的按需加载与精准共享。
- **工具管理要克制**：工具并非越多越好。必须精准筛选适合当前任务的工具，并严格保障参数 Schema 的正确性与工具执行的稳定性。
- **长任务必须依赖机制保障**：拒绝无限循环的单 Agent 长连接，通过 DAG 工作流机制天然支持断点续传与容错，保证执行完整性。

此外，基础设施的支撑至关重要。我们构建了基于 **OpenTelemetry** 的全链路可观测体系，覆盖网关、链路追踪与日志，实现对 Agent 执行状态与模型调用的深度监控；同时强调 **Data For AI** 理念，通过数据源管理与数据关系表达增强模型对运维数据的理解。

## 总结与行动建议

多智能体系统的落地不仅是算法问题，更是复杂的工程体系问题。从静态工作流到 Multi-Agents，核心是通过 MCP 统一工具层、通过 DAG 保障确定性、通过上下文工程突破认知瓶颈。

**行动建议**：
1. **工具层标准化**：新启动的项目优先采用 MCP 协议对接工具与沙箱，避免碎片化集成。
2. **复杂任务 DAG 化排**：面对多步诊断或执行链路，尽早引入 Planner + DAG 拆解任务，不要依赖单 Agent 的隐式规划。
3. **建设数据飞轮**：从第一天起建设基于 OpenTelemetry 的可观测体系，收集诊断链路数据，利用反馈数据微调模型或优化 Prompt，形成“数据驱动迭代”的闭环。

## 开放问题与延伸方向

1. **MCP 参数防注入**：如何严格限制工具的参数 Schema 以防范大模型幻觉导致的非法参数注入？（关联工具稳定性原则）
2. **DAG 上下文共享机制**：子 Agent 间具体采用何种存储结构与数据结构传递中间态以防信息丢失？（关联上下文工程实践）
3. **DAG 死锁风险**：Planner 规划出逻辑死胡同时，DAG 强约束是否会导致链路死锁而非优雅降级？（关联架构容错设计）
4. **延迟与 Token 消耗**：引入 MCP 和 DAG 后，系统延迟与 Token 消耗是否会随 Agent 数量指数级上升？（关联架构平衡原则）
5. **低质反馈数据**：运维场景缺乏显式正确标签，如何避免低质反馈数据通过飞轮导致模型退化？（关联数据驱动迭代）
6. **可观测性转反思记忆**：OpenTelemetry 链路 Trace 能否直接转化为 Agent 的反思记忆以提升后续规划成功率？（关联可观测体系价值扩展）
7. **动态工具挂载**：能否引入向量检索按需召回工具，替代静态全量暴露给 Planner？（关联工具管理克制原则）
8. **事件驱动 Actor 模型**：除 DAG 预编排外，是否考虑异步 Actor 模型处理 PaaS 长时等待与高并发诊断？（关联架构选择平衡）
9. **DAG 配置僵化**：业务要求快速新增诊断流时，如何避免 DAG 僵化导致开发效率倒退回静态工作流时代？（关联架构复杂度取舍）
10. **多智能体评估指标**：除最终准确率，如何量化评估“Agent 协作过程”的效率、鲁棒性与上下文利用率？（关联模型评估体系）
