## Agent Harness 成熟度模型 (AHMM)

| 级别 | 名称 | 特征 | 代表项目 | 2026现状 |
|------|------|------|---------|---------|
| L1 | 能力验证 | 单场景 Demo 可跑 | BabyAGI, Crawl4AI | 已跨越 |
| L2 | 组件化 | 模块可组合替换 | LangChain, CrewAI, OpenAI Agents SDK | 当前主流 |
| L3 | 可观测 | 链路追踪+评估闭环 | LangSmith, OpenClaw, Weave | 部分达到 |
| L4 | 弹性伸缩 | 动态调度+容错自愈 | Dify(企业版), Coze, Amazon Bedrock Agent | 少数达到 |
| L5 | 自治运维 | Agent 自监控自修复 | Google A2A, AG2 | 探索中 |

**定义：** 衡量 Agent 开发框架/运行时从原型到生产就绪的五级成熟度模型。L1 能力验证 → L2 组件化 → L3 可观测 → L4 弹性伸缩 → L5 自治运维。大多数框架当前处于 L2-L3 之间。

## Agent 编排四范式

| 范式 | 特点 | 适用场景 | 代表实现 | 局限 |
|------|------|---------|---------|------|
| 线性链 (Chain) | 固定顺序，简单可靠 | 单任务Pipeline | LangChain Chain, OpenAI Agents SDK | 不支持分支 |
| DAG (有向图) | 并行+依赖，高效 | 多步骤编排 | LangGraph, ControlFlow | 需预定义拓扑 |
| 事件驱动 (EDA) | 解耦+实时，灵活 | 响应式Agent | Inngest, Trigger.dev | 调试复杂 |
| 自治协作 (Autonomous) | Agent自决策，弹性 | 复杂探索任务 | AG2, CrewAI, Google A2A | 可控性弱 |

**定义：** Agent 编排架构的四种基本范式：线性链（Chain）、有向无环图（DAG）、事件驱动（Event-Driven）、自治协作（Autonomous）。实际系统通常是多种范式的混合。

## 1. 框架演进判断

**判断一：Agent 框架正从“单步推理调度”向“长程自治与状态机管理”演进。**
*   **论据**：传统框架依赖线性 Prompt 传递，而今日动态中 MetaGPT、AutoGen 等均在强化多智能体角色化与状态流转。论文《Locating and Closing Information Gaps in Multi-Agent Systems》明确指出，单线传递会导致信息断层，需要引入证据校验和闭环修正机制。
*   **对开发者的影响**：开发者不能再将 LLM 视为简单的 API 调用点，而需将其视为带有内部状态的独立实体。必须引入显式的状态机或工作流引擎来管理 Agent 的中断、恢复与纠错。

**判断二：多智能体协作框架的竞争壁垒从“通信协议”转移到“领域工作流封装”。**
*   **论据**：TauricResearch/TradingAgents 作为一个垂直金融交易框架上榜，说明通用多智能体框架（如 AutoGen）的通信底座已趋同。真正的增量价值在于封装特定领域的专业 SOP（如金融分析、软件开发）。MetaGPT 定位“AI 软件公司”也是同一逻辑。
*   **对开发者的影响**：通用框架适合造轮子和探索，但在落地业务时，应优先参考或构建带有强领域属性的 Agent 架构，减少从零编排通用框架的试错成本。

**判断三：评测与可观测性已成为制约 Agent 走向生产的硬性瓶颈。**
*   **论据**：今日动态中 EnvOS（针对计算机使用 Agent 的审计）和 Ramanujan Challenge（多格式证明评估管线）直指 Agent 评测痛点。传统单点断言已失效，必须基于“现象级任务构建”和“证据链”进行评估。
*   **对开发者的影响**：没有观测就没有生产。开发者在设计 Agent 架构的第一天就必须内建评测与审计模块，记录每一步的推理上下文、工具调用结果与环境状态变更。

## 2. 编排模式分析（基于 Agent 编排四范式）

今日动态反映出编排趋势正从低级范式向高级范式加速渗透，单一范式已无法满足复杂业务，**混合编排成为主流**。

*   **线性链**：适合简单 RAG 与固定工具调用。今日论文《Retrieving from Your Own Mistakes》表明，即使是线性 RAG，也需要引入“基于错误的在线策略训练”来动态调整检索链路，纯静态线性链的鲁棒性不足。
*   **DAG（有向无环图）**：在需要并行处理多分支任务的场景胜出。例如同时进行多源数据检索与交叉验证。适合任务边界清晰、可分解的批处理作业。
*   **事件驱动**：在动态环境交互中胜出。EnvOS 论文揭示，当 Agent 操作计算机时，“世界在变化”，必须采用事件驱动机制来捕获环境反馈，处理异步状态变更和意外弹窗。
*   **自治协作**：在探索性研究与复杂创意任务中胜出。MetaGPT 和 TradingAgents 体现了多角色（如研究员、交易员、风控员）通过自然语言进行辩论、协作与共识达成的过程。

**混合编排最佳实践**：
采用 **“宏观自治协作 + 微观 DAG/事件驱动”** 架构。顶层使用自治协作范式分配角色与宏观目标（如 TradingAgents 分配分析师和交易员），底层在单个 Agent 执行具体任务时，降级为 DAG 或事件驱动（如触发数据抓取、并行计算指标、监听市场异动事件），以平衡灵活性与确定性。

## 3. 工程实践建议

**建议一：框架选型应遵循“控制力优先，领域次之，通用兜底”原则。**
*   **可操作**：如果你的任务是高度确定性的流程（如固定报表生成），直接使用传统 DAG 工作流引擎（如 Airflow/Prefect）内嵌 LLM 节点，不要强行套用重型 Agent 框架；如果是多角色协作任务，优先选用带有状态管理和消息池机制的框架（如 AutoGen 的 GroupChat 或 MetaGPT），并强制引入一个 "Observer/Grader" 角色负责质量把控。

**建议二：从 L2（单 Agent+工具）向 L3（多 Agent 协作）升级时，优先构建“信息共享黑板”而非点对点通信。**
*   **可操作**：参考《Locating and Closing Information Gaps》的发现，不要让 Agent A 直接把自然语言结果传给 Agent B（容易产生幻觉和信息丢失）。应建立一个结构化的共享内存（Blackboard Pattern），所有 Agent 读取和写入结构化证据片段，并在最终输出前由专门的 Receiver Agent 进行 Gap Closing（信息缺口弥合）校验。

**建议三：生产环境必须引入“环境快照”与“基于现象的回放审计”机制。**
*   **可操作**：针对 Computer-Use 或外部环境交互的 Agent，参考 EnvOS 的设计。在每次工具调用前后，序列化环境状态（如 DOM 树快照、数据库事务 ID）；在评测阶段，不要仅看最终结果，而要构建“现象级任务”（如：文件是否被正确重命名？进程是否被杀死？），通过 Evidence-Based Grader 自动比对快照日志，确保 Agent 行为可追溯、可回滚。

## 4. FAQ：关于 Agent Harness 的常见问题

**Q1: LangChain、AutoGen 和 MetaGPT 在架构定位上的核心区别是什么？**
**A:** 
*   **LangChain** 是“组件化工具库”，偏向 L2 单 Agent 的线性链与工具集成，强调接口丰富度，适合快速构建原型和简单应用。
*   **AutoGen** 是“多智能体通信底座”，偏向 L3 多 Agent 对话与事件驱动，核心在于定义 Agent 间的消息路由和对话轮次控制，适合需要多轮博弈与讨论的场景。
*   **MetaGPT** 是“SOP 驱动的多智能体框架”，偏向 L3+ 领域封装，将人类软件工程（或特定行业）的标准作业程序硬编码为 Agent 协作流程，适合需要强结构化输出的复杂工程任务。

**Q2: 在多智能体系统中，如何有效解决“信息断层”和“幻觉传递”问题？**
**A:** 采用结构化消息传递与闭环校验。不要传递自然语言总结，而是传递结构化的 JSON 证据（包含源引用、置信度）。引入专门的“审查 Agent”，在信息从 Sender 传递到 Receiver 之前，进行 Evidence-Based 校验，比对原始上下文与传递信息的一致性，截断不合规的信息流。

**Q3: 如何对具有副作用的 Agent（如 Computer-Use Agent）进行可靠的自动化评测？**
**A:** 抛弃纯文本相似度评测。采用“现象级任务构造”与“环境状态断言”。定义任务的成功标准不是 Agent 输出了什么，而是环境发生了什么改变（如：文件系统状态变化、API 调用日志记录）。通过沙盒环境执行 Agent，随后运行独立的 Grader 脚本去检查这些环境现象是否满足预期，从而实现客观评测。

## 常见问题

### Q: 2026年应该选哪个 Agent 框架？
A: 取决于场景。简单 RAG → LangChain/LlamaIndex；多步骤编排 → LangGraph/CrewAI；企业生产 → Dify 企业版 + Temporal；快速原型 → OpenClaw。核心选型标准不是功能多少，而是可观测性（L3）是否达标。

### Q: MCP 和 Function Calling 的区别是什么？
A: Function Calling 是模型能力（模型理解何时调用），MCP 是协议标准（定义工具如何被发现和接入）。MCP 解决工具生态互操作性，Function Calling 解决模型推理问题。两者互补不互斥。

### Q: Agent 框架从 L2 到 L3 最难跨越的是什么？
