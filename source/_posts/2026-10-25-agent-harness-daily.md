## Agent Harness 成熟度模型 (AHMM)

| 级别 | 名称 | 特征 | 代表项目 | 2026现状 |
|------|------|------|---------|---------|
| L1 | 能力验证 | 单场景 Demo 可跑 | BabyAGI, Crawl4AI | 已跨越 |
| L2 | 组件化 | 模块可组合替换 | LangChain, CrewAI, OpenAI Agents SDK | 当前主流 |
| L3 | 可观测 | 链路追踪+评估闭环 | LangSmith, OpenClaw, Weave | 部分达到 |
| L4 | 弹性伸缩 | 动态调度+容错自愈 | Dify(企业版), Coze, Amazon Bedrock Agent | 少数达到 |
| L5 | 自治运维 | Agent 自监控自修复 | Google A2A, AG2 | 探索中 |

**定义：** 衡量 Agent 开发框架/运行时从原型到生产就绪的五级成熟度模型。L1 能力验证 → L2 组件化 → L3 可观测 → L4 弹性伸缩 → L5 自治运维。大多数框架当前处于 L2-L3 之间。

## Agent 编排四范式

| 范式 | 特点 | 适用场景 | 代表实现 | 局限 |
|------|------|---------|---------|------|
| 线性链 (Chain) | 固定顺序，简单可靠 | 单任务Pipeline | LangChain Chain, OpenAI Agents SDK | 不支持分支 |
| DAG (有向图) | 并行+依赖，高效 | 多步骤编排 | LangGraph, ControlFlow | 需预定义拓扑 |
| 事件驱动 (EDA) | 解耦+实时，灵活 | 响应式Agent | Inngest, Trigger.dev | 调试复杂 |
| 自治协作 (Autonomous) | Agent自决策，弹性 | 复杂探索任务 | AG2, CrewAI, Google A2A | 可控性弱 |

**定义：** Agent 编排架构的四种基本范式：线性链（Chain）、有向无环图（DAG）、事件驱动（Event-Driven）、自治协作（Autonomous）。实际系统通常是多种范式的混合。

## 二、 编排模式分析

基于“Agent 编排四范式”，今日动态反映了以下编排趋势：

### 1. 趋势：从“自治协作”向“DAG与事件驱动”回撤
当前业界对早期盲目推崇的“自治多智能体协作”进行冷思考。由于 LLM 幻觉和上下文窗口限制，完全自治的 Agent 群容易陷入死循环或偏离目标。趋势是向 **DAG（有向无环图）** 和 **事件驱动** 退化，以牺牲部分灵活性换取业务的确定性。

### 2. 范式胜出场景分析
*   **线性链**：**简单工具调用场景胜出**。如简单的 RAG 问答、单步信息抽取。使用 LangChain 基础 LCEL 即可，轻量高效。
*   **DAG（有向无环图）**：**复杂业务流场景胜出**。如 MetaGPT 中的软件工程流（需求分析->架构设计->编码->测试），以及绝大多数企业级 SOP。通过显式定义节点和边，确保执行路径的可预测性。
*   **事件驱动**：**长时运行与异步任务场景胜出**。如金融交易监控、运维告警处理。AutoGen 中的部分异步交互模式适用于需要等待外部系统反馈的场景。
*   **自治协作**：**探索性研究与头脑风暴场景胜出**。如 TradingAgents 中模拟多空双方的辩论。此范式仅适合容错率极高或有人类实时监督的沙盒环境。

### 3. 混合编排最佳实践
生产级 Agent 应采用**“宏观 DAG + 微观自治”**的混合编排模式：
*   **宏观层面**：使用 DAG（如 LangGraph）定义业务主干流，强制规定阶段流转条件（Gatekeeper），确保流程可控。
*   **微观层面**：在特定的单个节点内（如“代码审查”节点），允许多个 Agent（如 Coder、Reviewer）进行短时的自治辩论，但在达到 Token 上限或轮次上限前必须强制收敛结果并返回主干流。

## 三、 工程实践建议

### 1. 框架选型建议：按“控制粒度”而非“知名度”选型
*   **需要极致控制力与复杂状态机**：首选 **LangGraph**。其基于图的结构和内置的持久化层，最适合构建需要频繁人工介入和回滚的生产级 Agent。
*   **需要快速构建多角色对话与研究型 Agent**：首选 **AutoGen**。其基于对话驱动的模式在构建探讨型多智能体时开发效率最高。
*   **需要模拟企业级 SOP 流水线**：参考 **MetaGPT** 的设计哲学，将标准化的软件工程实践封装为不同 Agent 的行为约束。

### 2. 从 L2（部分自治）到 L3（条件自治）的升级路径
*   **Step 1：引入结构化输出**。强制 Agent 输出 JSON Schema（如 OpenAI Function Calling），将非结构化文本转化为可被代码解析的状态，这是从 L2 迈向 L3 的基石。
*   **Step 2：构建动态路由（条件边）**。在编排框架中引入基于规则或小模型的路由节点。当 Agent 置信度低于阈值���，强制降级为人工处理或切换至静态规则流。
*   **Step 3：植入短期记忆与反思机制**。在关键节点后增加 Eval Agent（评估智能体），对主 Agent 的输出进行打分。若分数不达标，触发自我修正循环，而非直接放行。

### 3. 生产环境注意事项
*   **超时与熔断机制**：LLM 推理延迟不可控，必须在运行时层设置严格的单步超时时间。一旦超时，必须能捕获异常并流转至降级策略（如返回固定话术或转人工）。
*   **沙盒化工具执行**：对于需要执行代码或系统命令（如 Bash 命令）的 Agent，必须部署在如今日动态提到的 LinuxArena 等沙盒环境中，严格限制文件系统和网络访问权限，防止 Agent 越权操作。
*   **全链路状态追踪**：必须为每个 Agent 执行分配唯一的 Trace ID，并在编排层将所有子 Agent 的调用、工具执行、Token 消耗打标上报至可观测性平台，这是后续优化 Prompt 和控制成本的核心依据。

## 四、 Agent Harness 常见问题（FAQ）

**Q1：在构建 Agent 应用时，应该选择从零自研编排层，还是使用 LangChain/AutoGen 等开源框架？**
**A：** 建议初期采用开源框架（如 LangGraph）作为底座，但将业务逻辑与框架解耦。自研编排层初期成本极高，且难以覆盖各种边缘情况（如重试、并发控制、状态持久化）。开源框架提供了这些基础设施，但其核心价值在于“胶水”作用。开发者应将精力集中在业务 Prompt 设计、工具定义和评估体系构建上。当业务复杂度极高且框架成为性能瓶颈时，再考虑抽象替换底层运行时。

**Q2：多智能体框架在真实业务中往往容易“跑飞”（偏离目标），如何解决？**
**A：** 解决“跑飞”的核心是引入强约束的编排机制。1）限制对话轮次：在多智能体交互中设置最大轮次，达到后强制总结并退出；2）引入 Supervisor Agent：设置一个不参与具体执行，仅负责监督其他 Agent 输出是否符合预期目标的“主管 Agent”；3）使用 DAG 替代自由对话：将多智能体交互固化为有向无环图，每个节点的输入输出格式严格定义，杜绝无意义的互相吹捧或扯皮。

**Q3：Agent 框架中的“记忆”模块通常如何工程化实现？**
**A：** 生产级 Agent 记忆不应依赖无脑扩大上下文窗口，而应采用分层架构。**短期记忆**：利用框架的 Checkpoint 机制，将当前对话状态序列化存储在 Redis/PostgreSQL 中，支持中断恢复；**长期记忆**：将历史交互通过 LLM 提取为结构化事实或向量化存入 Vector DB。在每次任务开始时，通过 RAG 机制检索相关记忆注入 Prompt。对于时序性极强的任务，还需引入时间感知的检索策略，优先召回近期高权重记忆。

## 常见问题

### Q: 2026年应该选哪个 Agent 框架？
A: 取决于场景。简单 RAG → LangChain/LlamaIndex；多步骤编排 → LangGraph/CrewAI；企业生产 → Dify 企业版 + Temporal；快速原型 → OpenClaw。核心选型标准不是功能多少，而是可观测性（L3）是否达标。

### Q: MCP 和 Function Calling 的区别是什么？
A: Function Calling 是模型能力（模型理解何时调用），MCP 是协议标准（定义工具如何被发现和接入）。MCP 解决工具生态互操作性，Function Calling 解决模型推理问题。两者互补不互斥。

### Q: Agent 框架从 L2 到 L3 最难跨越的是什么？
A: 可观测性闭环——不只是能看到 trace，还要能基于 trace 自动评估、归因、优化。大多数框架有 tracing，但缺少从 trace 到 improvement 的自动回路。
