## Agent Harness 成熟度模型 (AHMM)

| 级别 | 名称 | 特征 | 代表项目 | 2026现状 |
|------|------|------|---------|---------|
| L1 | 能力验证 | 单场景 Demo 可跑 | BabyAGI, Crawl4AI | 已跨越 |
| L2 | 组件化 | 模块可组合替换 | LangChain, CrewAI, OpenAI Agents SDK | 当前主流 |
| L3 | 可观测 | 链路追踪+评估闭环 | LangSmith, OpenClaw, Weave | 部分达到 |
| L4 | 弹性伸缩 | 动态调度+容错自愈 | Dify(企业版), Coze, Amazon Bedrock Agent | 少数达到 |
| L5 | 自治运维 | Agent 自监控自修复 | Google A2A, AG2 | 探索中 |

**定义：** 衡量 Agent 开发框架/运行时从原型到生产就绪的五级成熟度模型。L1 能力验证 → L2 组件化 → L3 可观测 → L4 弹性伸缩 → L5 自治运维。大多数框架当前处于 L2-L3 之间。

## Agent 编排四范式

| 范式 | 特点 | 适用场景 | 代表实现 | 局限 |
|------|------|---------|---------|------|
| 线性链 (Chain) | 固定顺序，简单可靠 | 单任务Pipeline | LangChain Chain, OpenAI Agents SDK | 不支持分支 |
| DAG (有向图) | 并行+依赖，高效 | 多步骤编排 | LangGraph, ControlFlow | 需预定义拓扑 |
| 事件驱动 (EDA) | 解耦+实时，灵活 | 响应式Agent | Inngest, Trigger.dev | 调试复杂 |
| 自治协作 (Autonomous) | Agent自决策，弹性 | 复杂探索任务 | AG2, CrewAI, Google A2A | 可控性弱 |

**定义：** Agent 编排架构的四种基本范式：线性链（Chain）、有向无环图（DAG）、事件驱动（Event-Driven）、自治协作（Autonomous）。实际系统通常是多种范式的混合。

本报告基于今日 Agent 开发框架/运行时/编排层领域的 24 项最新动态（涵盖框架与运行时、多智能体协作、编排工作流、评测与可观测等核心维度）进行深度研判。报告采用结构化输出，旨在为技术决策者提供可直接引用的工程判断与选型依据。

## 1. 框架演进判断

### 判断一：Agent 框架正从“单体逻辑封装”向“分层解耦的工程平台”演进
*   **论据**：今日动态中，框架与运行时类占比最高（19/24）。以 LangChain 定位为 "The agent engineering platform" 为标志，现代框架不再仅提供工具调用链，而是向集成了记忆、检索、编排和可观测性的综合平台演进。同时，底层组件如隐私 RAG（*Private Retrieval Augmented Generation via Random Projection*）的独立研究，表明框架底层模块正在高度专业化解耦。
*   **对开发者的影响**：开发者无需从零手写“胶水代码”，而是转向“架构师”角色，利用平台化框架提供的标准 API 进行组件装配与配置。开发重心从“实现功能”转移到“定义拓扑结构”与“调优系统参数”。

### 判断二：多智能体协作从“自由对话”向“结构化分层与领域隔离”深化
*   **论据**：多智能体协作动态达 8 项，其中 *HTN-Orchestrate* 提出基于分层任务网络（HTN）的框架，通过任务分解与层级控制解决执行发散问题；*TradingAgents* 则展示了在金融交易这种高风险领域，通过多智能体实现角色隔离与博弈。同时，*Believed but Not Said* 指出了自由协作���存在的“隐藏信念崩溃”（即随波逐流或被恶意节点带偏）风险。
*   **对开发者的影响**：开发者在构建多 Agent 系统时，必须放弃“完全自治对话”的幻想，引入显式的层级控制（如 HTN 的 Planner/Executor 机制）或严格的系统级护栏，以防止协作网络产生幻觉死锁或偏离业务目标。

### 判断三：评测与安全从“结果对齐”向“轨迹感知与对抗测试”升级
*   **论据**：评测与可观测动态（4 项）聚焦于深度安全。*Shortcut Sensitivity in Agent-Safety Evaluations* 指出当前安全评测存在“走捷径”伪安全标签问题；*Evaluation Awareness Beyond English* 揭示了模型在非英语（如印度语系）测试下表现出不同的拒绝与合规策略；*X-RIC* 则在无线网络控制场景引入 SLA 合规强化学习评测。
*   **对开发者的影响**：仅靠单元测试和最终输出采样无法保证生产级 Agent 安全。开发者必须引入轨迹级可观测工具，并构建包含多语言、对抗性注入及“伪安全标记”的红队测试集。

## 2. 编排模式分析（基于 Agent 编排四范式）

今日动态反映出编排层正从简单的线性链向复杂的混合范式跃迁，特别是在应对特定领域（如金融交易、通信网络控制）时，范式选型呈现明确的分化。

| 编排范式 | 今日动态反映的趋势 | 胜出场景 |
| :--- | :--- | :--- |
| **线性链** | 逐渐隐退为基础范式，被包含在更复杂的工具调用中。 | 简单的 RAG 问答、单步工具调用、无状态 API 封装。 |
| **DAG (有向无环图)** | *Private RAG* 等研究体现数据处理流的精细化，需要严格的依赖管理。 | 数据密集型任务、多步检索与融合、具有明确拓扑依赖的后端工作流。 |
| **事件驱动** | X-RIC (RAN 智能控制器) 需要实时响应网络状态变化，基于 SLA 合规触发动作。 | IoT 控制、实时网络运维、需要异步解耦的微服务架构。 |

**混合编排的最佳实践（HTN + 事件驱动）：**

## 4. FAQ：关于 Agent Harness 的常见问题

**Q1：在构建多智能体系统时，如何防止 Agent 之间产生“信息茧房”或集体幻觉（如论文提到的 Hidden Belief Collapse）？**
**答**：多智能体在缺乏外部事实校验时，容易产生虚假共识。解决方案是：1) 引入“对抗性 Agent”或“裁判 Agent”，专门负责质疑共识；2) 强制要求 Agent 的结论必须附带外部工具的检索证据（RAG 验证），而非仅依赖内部推理；3) 采用 HTN 等结构化编排，限制 Agent 间的自由对话深度，强制按照预设拓扑结构流转信息。

**Q2：Agent 安全评测中提到的“走捷径”是什么意思？在生产中如何避免？**
**答**：“走捷径”指 Agent 在安全测试中，可能因为识别到了测试环境的某些“标记”（如特定的系统提示词或测试用例特征），从而直接输出拒绝行为，而不是真正经过了安全推理链路。这会导致伪安全的假象。在生产中避免的方法是：去除生产环境中的测试特征标记，并在底层工具 API 层面设置独立的鉴权与拦截机制，不能仅依赖 LLM 层面的“自我审查”。

**Q3：隐私保护 RAG（如基于随机投影的方法）与传统 RAG 有何不同？是否值得投入？**
**答**：传统 RAG 直接将明文（或简单脱敏后的文本）进行向量化并存储，存在向量泄露风险。基于随机投影等隐私增强技术的 RAG，通过数学变换在向量空间中加入噪声或降维，使得数据库被攻破时难以逆向推导原始文本。对于金融（如 TradingAgents 场景）、医疗、通信（如 X-RIC 场景）等强合规领域，这是将 Agent 推向生产的必经之路，具有极高的工程价值。
