## Agent Harness 成熟度模型 (AHMM)

| 级别 | 名称 | 特征 | 代表项目 | 2026现状 |
|------|------|------|---------|---------|
| L1 | 能力验证 | 单场景 Demo 可跑 | BabyAGI, Crawl4AI | 已跨越 |
| L2 | 组件化 | 模块可组合替换 | LangChain, CrewAI, OpenAI Agents SDK | 当前主流 |
| L3 | 可观测 | 链路追踪+评估闭环 | LangSmith, OpenClaw, Weave | 部分达到 |
| L4 | 弹性伸缩 | 动态调度+容错自愈 | Dify(企业版), Coze, Amazon Bedrock Agent | 少数达到 |
| L5 | 自治运维 | Agent 自监控自修复 | Google A2A, AG2 | 探索中 |

**定义：** 衡量 Agent 开发框架/运行时从原型到生产就绪的五级成熟度模型。L1 能力验证 → L2 组件化 → L3 可观测 → L4 弹性伸缩 → L5 自治运维。大多数框架当前处于 L2-L3 之间。

## Agent 编排四范式

| 范式 | 特点 | 适用场景 | 代表实现 | 局限 |
|------|------|---------|---------|------|
| 线性链 (Chain) | 固定顺序，简单可靠 | 单任务Pipeline | LangChain Chain, OpenAI Agents SDK | 不支持分支 |
| DAG (有向图) | 并行+依赖，高效 | 多步骤编排 | LangGraph, ControlFlow | 需预定义拓扑 |
| 事件驱动 (EDA) | 解耦+实时，灵活 | 响应式Agent | Inngest, Trigger.dev | 调试复杂 |
| 自治协作 (Autonomous) | Agent自决策，弹性 | 复杂探索任务 | AG2, CrewAI, Google A2A | 可控性弱 |

**定义：** Agent 编排架构的四种基本范式：线性链（Chain）、有向无环图（DAG）、事件驱动（Event-Driven）、自治协作（Autonomous）。实际系统通常是多种范式的混合。

## 深度分析

# Agent Harness 领域动态深度报告：从自治协作到混合编排的工程跃迁

> **数据洞察摘要**：今日 Agent Harness 领域共监测到 23 项核心动态。框架与运行时（19）及多智能体协作（8）占据主导地位。学术界正密集探索多会话交替、强化学习纠偏与饱和度评测，而工程界则持续押注金融交易、软件工程等垂直多智能体场景。**核心判断：Agent 框架正从“单点工具调用”向“多会话、混合编排的工程平台”演进。**

---

## 1. 框架演进判断

**判断一：Agent 框架正从“单次推理工具调用”向“多会话、多阶段交替”演进。**
*   **论据**：今日多篇论文（如 *Humanize MLE Agents* 提出的 Multi-Agent Session Alternation，*MENTOR* 提出的基于失败学习的强化学习干预）表明，单次单Agent执行已触及能力天花板。通过引入多会话交替和基于策略的纠偏机制，能有效解决模型在复杂任务中的“崩溃”和“浪费”问题。
*   **对开发者的影响**：开发者不能再将 Agent 视作无状态的 API 调用器。Harness 必须支持状态持久化、会话挂起与恢复，以及基于历史失败轨迹的动态策略调整。

**判断二：新兴垂直多智能体框架正在成熟通用框架的夹击中开辟细分赛道。**
*   **论据**：虽然 LangChain 定位为“The agent engineering platform”，MetaGPT 持续深耕“AI 软件公司”，但 TradingAgents 等新兴框架凭借内置金融领域的专业分析、风控多智能体协作流，成功切分垂直市场。
*   **对开发者的影响**：通用框架（LangChain 等）适合做基础设施和长尾场景，但在金融、代码生成等高价值领域，采用或借鉴垂直多智能体框架的预设 SOP（标准作业程序）能大幅缩短试错周期。

**判断三：架构选型需从“模型能力中心”转向“编排与评测中心”。**
*   **论据**：*SqueezeBench* 提出的抗饱和评测，以及 *Humanize Olympiad Agents* 中的 Solve-Review-Wiki-Verify 工作流证明，决定 Agent 上限的不再是单纯的基座模型，而是如何通过编排（Review/Verify）榨取模型潜力，并通过抗饱和评测真实反映能力。
*   **对开发者的影响**：选型时应优先考虑框架是否具备细粒度的过程编排能力（如 DAG 和事件驱动）以及内置的防作弊/防饱和评测模块，而非仅仅看重集成了多少工具。

---

## 2. 编排模式分析

基于“Agent 编排四范式”，今日动态反映出以下趋势：

*   **线性链**：正在退化为最基础的工具调用层，多用于简单 RAG 或单步搜索。
*   **DAG（有向无环图）**：在确定性工作流中胜出。例如 *Humanize Olympiad Agents* 的 Wiki-Verify 流程，确保了输出结果的严谨性和可验证性。适合对准确性要求极高的代码生成、数学证明场景。
*   **事件驱动**：在动态资源调度和异步多智能体交互中崭露头角。当 Agent A 完成代码审查，触发事件通知 Agent B 执行测试，解耦了系统组件。
*   **自治协作**：在探索性任务中表现活跃。如 TradingAgents 中多角色（基本面、技术面、情绪面分析师）的自治讨论与博弈。

**哪种范式在什么场景下胜出？**
*   **高确定性、高容错要求场景**（如金融交易执行、奥赛题解答）：**DAG 范式胜出**。通过强制引入 Review 和 Verify 节点，消除单点幻觉。
*   **高探索性、信息聚合场景**（如市场情绪分析、MLE 模型架构搜索）：**自治协作范式胜出**。允许 Agent 自由讨论以激发涌现能力。

**混合编排的最佳实践：**
今日动态强烈指向**“宏观 DAG + 微观自治”的混合编排模式**。
*   **实践方案**：在 Harness 层面，首先通过 DAG 定义宏观工作流（如：Solve -> Review -> Verify），保证流程可控；在微观节点内部（如 Solve 节点），允许多个 Agent 进行自治协作与辩论。这种模式兼顾了系统的鲁棒性与灵活性。

## 3. 工程实践建议

1.  **框架选型建议：采用“底座 + 插件”分层架构**
    *   底座选择 LangChain 等成熟框架处理基础的工具绑定、记忆管理和 LLM 抽象。
    *   业务层开发自研编排插件，或引入 MetaGPT 的 SOP 机制。不要试图用一个框架解决所有问题，将领域逻辑（如 TradingAgents 的风控规则）与通用 Harness 解耦。

2.  **从 L2（单Agent+工具）到 L3（多Agent协作）的升级路径**
    *   **第一步：角色拆分**。将单体 Agent 拆分为 Planner（规划）、Executor（执行）、Critic（审查）三个独立 Agent。
    *   **第二步：引入失败干预机制**。参考 *MENTOR* 论文，在 Critic 节点后增加 On-Policy 策略模块。当 Executor 失败时，不直接重试，而是由策略模块生成指导性提示，引导 Executor 纠偏。
    *   **第三步：实现会话交替**。参考 *Humanize MLE Agents*，让不同 Agent 在不同 Session 中接力工作，避免单 Agent 上下文窗口溢出导致的性能退化。

3.  **生产环境注意事项**
    *   **引入抗饱和评测**：参考 *SqueezeBench*，生产环境必须部署过程评测机制，防止 Agent 陷入“看似合理实则重复”的饱和输出死循环。
    *   **状态与记忆隔离**：在多会话交替时，确保短期工作记忆与长期事实记忆（如 Wiki 模块）物理隔离，防止早期错误污染后续推理。
    *   **资源熔断机制**：自治协作极易引发死循环或成本失控。Harness 必须强制配置最大轮次限制和 Token 消耗阈值。

## 4. FAQ：关于 Agent Harness 的常见问题

**Q1：在多智能体系统中，如何平衡自治协作的高成本与 DAG 工作流的低灵活性？**
**答：** 采用“宏观 DAG + 微观自治”的混合编排。在宏观流程上使用 DAG 确保关键节点的强制审查和流程可控（如必须经过 Verify 节点）；在具体执行节点内部，允许 Agent 进行有限轮次的自治讨论。同时，通过事件驱动机制实现节点间的异步通信，避免阻塞造成的性能浪费。

**Q2：Agent 框架从单会话升级到多会话交替，主要解决什么工程痛点？**
**答：** 主要解决“上下文窗口溢出”和“长程任务遗忘”痛点。单 Agent 在处理长程任务时，历史错误轨迹会污染上下文，导致性能崩溃。多会话交替允许系统将任务切片，每个子 Agent 在干净的上下文中执行特定子任务，并通过外部记忆库（如 Wiki）传递关键信息，从而大幅提升长程任务的成功率。

**Q3：如何评估一个 Agent Harness 是否具备生产级可用性？**
**答：** 考察三个核心指标：1) **可观测性**：是否支持细粒度的 Token 消耗追踪和每一步推理的 Trace 查看；2) **容错与干预**：是否内置类似 MENTOR 的失败干预策略，而非简单的错误重试；3) **抗饱和能力**：是否具备检测 Agent 陷入循环输出的评测机制，并能主动熔断重启。
