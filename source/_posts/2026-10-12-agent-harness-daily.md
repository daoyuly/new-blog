## Agent Harness 成熟度模型 (AHMM)

| 级别 | 名称 | 特征 | 代表项目 | 2026现状 |
|------|------|------|---------|---------|
| L1 | 能力验证 | 单场景 Demo 可跑 | BabyAGI, Crawl4AI | 已跨越 |
| L2 | 组件化 | 模块可组合替换 | LangChain, CrewAI, OpenAI Agents SDK | 当前主流 |
| L3 | 可观测 | 链路追踪+评估闭环 | LangSmith, OpenClaw, Weave | 部分达到 |
| L4 | 弹性伸缩 | 动态调度+容错自愈 | Dify(企业版), Coze, Amazon Bedrock Agent | 少数达到 |
| L5 | 自治运维 | Agent 自监控自修复 | Google A2A, AG2 | 探索中 |

**定义：** 衡量 Agent 开发框架/运行时从原型到生产就绪的五级成熟度模型。L1 能力验证 → L2 组件化 → L3 可观测 → L4 弹性伸缩 → L5 自治运维。大多数框架当前处于 L2-L3 之间。

## Agent 编排四范式

| 范式 | 特点 | 适用场景 | 代表实现 | 局限 |
|------|------|---------|---------|------|
| 线性链 (Chain) | 固定顺序，简单可靠 | 单任务Pipeline | LangChain Chain, OpenAI Agents SDK | 不支持分支 |
| DAG (有向图) | 并行+依赖，高效 | 多步骤编排 | LangGraph, ControlFlow | 需预定义拓扑 |
| 事件驱动 (EDA) | 解耦+实时，灵活 | 响应式Agent | Inngest, Trigger.dev | 调试复杂 |
| 自治协作 (Autonomous) | Agent自决策，弹性 | 复杂探索任务 | AG2, CrewAI, Google A2A | 可控性弱 |

**定义：** Agent 编排架构的四种基本范式：线性链（Chain）、有向无环图（DAG）、事件驱动（Event-Driven）、自治协作（Autonomous）。实际系统通常是多种范式的混合。

## 深度分析

# Agent Harness 领域动态深度报告：从单点工具到多智能体工程化演进

**报告概览**：今日 Agent Harness（开发框架/运行时/编排层）领域共监测到 23 条有效动态。从数据分布来看，“框架与运行时”（19条）与“多智能体协作”（8条）占据绝对主导，表明行业已跨越单 Agent 探索期，全面进入多智能体系统（MAS）的工程化深水区。学术界的焦点集中于多会话工作流、基于强化学习的失败学习机制以及防饱和评测；工业界则持续巩固 LangChain 的平台地位与 MetaGPT 的多智能体编程范式。

以下是本日的深度分析与判断：

---

## 1. 框架演进判断

**判断一：Agent 框架正从“静态工具调用”向“多会话自治与强化学习反馈”演进。**
*   **论据**：今日多篇论文（如 *Humanize MLE Agents* 提出 Multi-Agent Session Alternation，*MENTOR* 提出基于失败经验的策略干预）表明，单次线性执行的 Agent 已触及能力天花板。现代框架必须支持长周期、多会话的状态保持与基于反馈的自我修正。
*   **对开发者的影响**：开发者需要将关注点从单纯的 Prompt 工程转移到“上下文工程”与“奖励函数设计”上。框架选型时，需重点考察其对长程记忆、会话中断恢复及 RLHF/GRPO 等强化学习范式的原生支持度。

**判断二：成熟通用框架与垂直领域多智能体框架形成“底座+插件”的共生格局。**
*   **论据**：GitHub 动态显示，LangChain 持续巩固其作为 “Agent Engineering Platform” 的底座地位，而 TradingAgents（金融交易）和 MetaGPT（软件工程）等垂直框架则在特定复杂场景下大放异彩。通用框架解决“能用”问题，垂直框架解决“好用”问题。
*   **对开发者的影响**：不建议在垂直领域从零造轮子。应采用“通用底座（如 LangChain/LangGraph）+ 垂直业务多智能体编排”的架构，将精力聚焦于业务逻辑与领域知识库的构建。

**判断三：评测与验证机制正成为 Agent 框架不可或缺的一等公民。**
*   **论据**：*SqueezeBench* 提出抗饱和数学能力评测，*Humanize Olympiad Agents* 强调 Solve-Review-Wiki-Verify 的闭环工作流。这反映出随着 Agent 自治能力提升，传统的“跑通即成功”的测试范式已失效，必须引入防作弊、防饱和的自动化验证层。
*   **对开发者的影响**：在架构设计中必须显式剥离出“Verify Agent”或“Reviewer”角色。生产级系统不能假设主 Agent 的输出绝对正确，必须通过框架级的编排强制走验证流程。

## 2. 编排模式分析（基于 Agent 编排四范式）

今日动态清晰反映了 Agent 编排范式在不同场景下的分化与收敛：

*   **线性链**：正在退化为最基础的构建块。仅适用于无状态、低风险的单一任务（如简单的 RAG 检索）。
*   **DAG（有向无环图）**：在工程化流水线中胜出。例如 *Humanize Olympiad Agents* 的 Solve -> Review -> Wiki -> Verify 流程，本质上是带条件分支的 DAG。**适用场景**：任务边界清晰、步骤可预期且需要强一致性的业务流程。
*   **事件驱动**：在动态资源调度与异步协作中展现潜力。*TradingAgents* 金融框架中多 Agent 对市场数据的实时响应即依赖事件驱动。**适用场景**：高并发、外部输入不可控、需要解耦的异步系统。
*   **自治协作**：探索前沿但工程风险极高。MetaGPT 模拟软件公司即属此类。**适用场景**：高容错、高创造性要求的探索性任务（如头脑风暴、原型生成）。

**混合编排的最佳实践**：
当前生产环境的最佳实践是**“宏观 DAG + 微观自治”**。即：在系统顶层采用 DAG 严格控制关键节点（如必须经过 Verify 节点），确保流程可控与可审计；在具体执行节点内部（如 Solve 节点），允许 Agent 采用自治协作模式进行多轮推理与工具调用。

## 3. 工程实践建议

**建议一：框架选型需遵循“状态管理优先”原则**
不要仅看框架支持多少工具。选型时重点测试框架对“状态”的处理能力：能否可视化修改 Graph 状态？能否在节点失败时进行 Time-travel（状态回溯）？推荐采用 LangGraph 等原生支持 Pregel 图计算模型的框架，以应对复杂的多智能体状态流转。

**建议二：从 L2（单 Agent 工具调用）到 L3（多智能体协作）的升级路径**
不要直接跳跃到完全自治的多智能体系统。推荐路径：
1.  **解耦业务流**：先用 L2 Agent 跑通核心链路，识别出瓶颈节点。
2.  **引入静态 Reviewer**：在关键节点后加入无状态的 LLM Reviewer（L2.5 阶段），形成简单的 Dual-Agent 线性链。
3.  **升级为动态 MAS**：当 Reviewer 逻辑复杂化后，将其拆分为 Wiki（知识检索）、Verify（逻辑校验）等独立 Agent，引入 DAG 编排，完成 L3 升级。

**建议三：生产环境必须构建“防崩溃与防退化”护栏**
参考论文 *MENTOR* 对“学习失败”的研究，生产环境需注意：
*   **熔断机制**：为每个 Agent 设置最大迭代次数与 Token 消耗上限，防止陷入死循环。
*   **On-Policy 监控**：监控 Agent 的行为轨迹是否偏离预设 Policy，一旦发现 Reward 信号坍塌（如 Agent 开始伪造工具调用结果），立即降级为人工接管或回退至简单规则引擎。

## 4. FAQ：关于 Agent Harness 的常见问题

**Q1：多智能体框架（如 MetaGPT/AutoGen）和单 Agent 框架（如 LangChain Agent Executor）的核心区别是什么？**
**A：** 核心区别在于**状态空间与通信机制**。单 Agent 框架主要维护单一的上下文窗口，依赖 ReAct 模式循环；多智能体框架则维护一个全局共享状态，Agent 之间通过消息传递（Message Passing）或状态读写进行通信，支持更复杂的角色分工、并发执行与拓扑结构（如 DAG 或星型）。

**Q2：在构建 Agent 系统时，何时应该引入多会话工作流？**
**A：** 当单次推理的上下文长度逼近模型极限，或任务需要“反思-修正”循环时，必须引入多会话工作流。例如论文 *Humanize MLE Agents* 所述，通过会话交替，让不同 Agent 在不同会话中接管任务，可以有效打破单 Agent 的上下文瓶颈，避免“遗忘”早期关键信息，并引入外部校验视角。

**Q3：Agent Harness 领域的“编排”与传统微服务编排（如 Kubernetes/Airflow）有何本质不同？**
**A：** 传统编排是**确定性的**，基于预定义的 DAG 和明确的 API 契约，失败原因是系统级（网络/超时）。Agent 编排是**非确定性的**，节点行为由 LLM 运行时生成，失败原因多为语义级（幻觉/逻辑错误）。因此，Agent Harness 需要具备语义级别的重试机制、基于 LLM 的动态路由能力以及上下文状态的持久化与回滚能力，这是传统编排系统不具备的。

### Q: 2026年应该选哪个 Agent 框架？

### Q: MCP 和 Function Calling 的区别是什么？
A: Function Calling 是模型能力（模型理解何时调用），MCP 是协议标准（定义工具如何被发现和接入）。MCP 解决工具生态互操作性，Function Calling 解决模型推理问题。两者互补不互斥。
